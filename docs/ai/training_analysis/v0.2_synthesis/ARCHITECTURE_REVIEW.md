# Training v0.2 Synthesis & v0.3 Architecture Review

**Status: `TRAINING_V0_2_SYNTHESIS_COMPLETE`**  
Scope: evidence review and design only. No dataset, Contract, Training Setup, evaluator, model output, or product code was changed; no training or inference was run.

## Decision

Prioritize one v0.3 experiment: an isolated, replayable **model-origin write-capability firewall at the Gateway boundary**. The evidence shows offline model outputs with direct-write attempts; it does not show that any RPC executed or that an absent Gateway caused those model errors. The repository Contract requires a proposal and trusted confirmation/recheck, while the AI Gateway is not implemented. Evaluate a stricter v0.3 boundary proposal: model-origin outputs are read-only; every model-origin write `tool_call` is denied, even if the model claims it is confirmed. After trusted UI confirmation, the Gateway itself assembles the canonical business command on a distinct trusted-UI/executor-origin path. This differs from portions of the frozen Contract that allow the orchestrator to acknowledge or convert a post-confirmation write `tool_call` (Contract lines 303, 405); this review proposes a future v0.3 permission boundary and does not change the current Contract. Keep raw model quality and execution-boundary safety as separate outcomes: blocking a bad call is not a correct business answer.

Do not infer that a 4B capacity ceiling has been demonstrated. Training examples contain only 36 business states across 171 surfaces; the held-out validation has 5 canonical states across 24 rows. The same `void_transfer`/L2 family appears in direct-write failures in A and C, and the visible inputs expose an opaque result ID without the transfer ID or confirmed entity binding required by the target. This is both an execution-safety problem and a data-solvability problem; it is not evidence that all write intents fail or that a larger model would fix it. Contract authority: `AI_MODEL_CONTRACT.md` lines 299–314, 394, 405–409; Scope lines 16–20, 64, 89–96.

## Does a single model step carry too many responsibilities?

The measured evidence is consistent with a heavily loaded single step: 171 training surfaces cover only 36 canonical business states; the longest proposal target is 665 tokens (proposal targets average about 508 tokens); C emits the expected read tool name on all 6/6 rows but has 0/6 valid payloads; and several expected answers require receipt bodies that are absent from the model-visible input. In the same step the model must route among six closed JSON output types, resolve user intent and entities, decide whether a read is needed, use visible business facts, produce nested proposal diffs and confirmation/execution fields, and serialize exact JSON. This supports a **plausible overloading hypothesis**, not a demonstrated overload or 4B capacity limit. These failures also have separate explanations: some inputs are underdetermined without receipt/entity bindings, the data covers relatively few states, and intent/tool/schema mappings fail even when a read tool name is correct. No experiment here isolates responsibility count from data visibility, schema, prompt, or model size.

## Contract and implementation boundary

The frozen Contract defines six closed output types and closed, type-specific structures. A `proposal` contains the intent and operation, preview/diff, confirmation level, and execution policy. A model `tool_call` is not proof of RPC success. L0 reads may call a tool; L1/L2 writes start as proposals and can only proceed after trusted UI confirmation and Gateway recheck. D4 expense financial edits stay non-executable with `execution_allowed=false` and `d4_atomic_update_not_supported`; confirmation cannot open that boundary. Proposal validity must be reconsidered when the page, Activity, selected entity, relevant server state, or financial version changes. See `AI_MODEL_CONTRACT.md` lines 299–314 and 394–409, plus `AI_SCOPE_FREEZE_V0.1.md` lines 16–20 and 64–96. The frozen Scope has 24 CORE, 21 GATED, 25 DEFERRED intents and 12 CORE, 13 GATED, 19 DEFERRED tools (`AI_SCOPE_FREEZE_V0.1.md` lines 46–64, 156, 315). The schema's `oneOf`, required fields, and `additionalProperties:false` establish shape constraints; they do not establish authorization or factual support (`docs/ai/schema/model_output.schema.json`, lines 89–141 and proposal branches around 2266–2351).

Intent/Snapshot metadata in `intent_catalog.json` and `tool_catalog.json` describes allowed scope and mappings; it is not itself an enforcing runtime. For example, Scope lines 89–96 call `void_transfer` a gated L2 proposal path. The catalog entry for that intent requires `activity_id`, `transfer_id`, and `void_reason` (`intent_catalog.json`, lines 1376–1403). The A/C direct calls therefore violate the required output path, and the visible opaque result ID does not satisfy the missing transfer binding.

The repository states that Gateway and adapters are not implemented (`AI_MODEL_CONTRACT.md` line 3; `AI_SCOPE_FREEZE_V0.1.md` line 3). A read-only search of `app/src/main` and `supabase/functions` found no AI Gateway/Tool Adapter implementation. Existing Supabase RPCs and database migrations are business operations, not an AI dispatch boundary. Therefore a proposed firewall is new runtime architecture to evaluate, not a description of current protection.

## Seven architecture directions

### 1. Make the model emit proposals for writes

**Evidence:** A cp36 direct-writes `void_transfer` on `sample_gs_p0_037`; C cp33 does so on `sample_teacher_4053b71f5faa`, while the corresponding v1 row asks for an ID. Both are the same L2 family with separate surface forms. Expected proposals are 0/3 correctly routed in A and C. **Hypothesis, unproven:** a small number of mixed route examples and underspecified guidance may make `tool_call` appear as a shortcut; the repeated errors could also reflect invisible binding requirements. **Change considered:** instead of merely prompting the model to emit proposals, evaluate a stricter design in which the model can emit only proposal/clarification for writes, and the Gateway assembles the canonical write command after trusted UI confirmation. Thus no model-origin write `tool_call` is allowed, including one that self-asserts confirmation. This is a future v0.3 boundary proposal; it is stricter than the frozen Contract's orchestrator acknowledge/convert path and does not amend that Contract here. **Risk:** over-clarification or incomplete/incorrect proposal fields; the trusted Gateway flow can also become a single point of rejection if it mishandles confirmation. **Minimum validation:** the offline origin-boundary replay below plus, later, a fresh sealed solvable write slice that checks proposal completeness and legal confirmed execution separately.

### 2. Narrow read-tool schemas to semantic arguments

**Evidence:** C has 6/6 expected debt calls with tool name `get_debt`, but 0/6 schema-valid; two also use disabled/mismapped `query_debt_summary`, while four have malformed/extra/missing fields. v0.1 reports visible IDs/tools but wrong intent or extra args on `sample_gs_p0_027` and `_028`. **Hypothesis, unproven:** generic or broad tool shapes and intent aliases contribute to route/argument errors. **Change:** expose only task-relevant semantic arguments for a selected read tool and reject extras deterministically. **Risk:** over-narrowing can remove valid filters or supporting lookups; a valid shape can still query the wrong entity. **Minimum validation:** one fixed-scope read schema/mapping round-trip over the six existing debt validation rows plus explicit unsupported-intent controls; report intent, tool, schema, and entity binding independently.

### 3. Parse and bind opaque IDs deterministically

**Evidence:** v0.1 `sample_gs_p0_032`/`_092` and C `sample_teacher_50f39996a01a` expose result IDs without needed receipt bodies. A/C void-transfer rows expose only an opaque result ID where GT requires a transfer ID. In B, the nine backend UUIDs do not match the legacy IDs. **Hypothesis, unproven:** asking the model to infer or reproduce identifiers encourages copying an unrelated ID or inventing bindings. **Change:** resolve entities from trusted selected-entity/server context or a validated lookup result; only pass server-bound IDs into an operation. **Risk:** stale/multiple candidate bindings can silently select the wrong entity. **Minimum validation:** deterministic collision/ambiguity/staleness cases plus replay of existing rows; unknown or unbound IDs must clarify or reject, never be guessed.

### 4. Enforce schema, allowlist, and write guards at runtime

**Evidence:** A/C show offline model outputs with unconfirmed direct writes; schema validity and Scope authorization are distinct. The Contract assigns allowlist, identity, version, confirmation, and server-result checks to a Gateway, but no Gateway is implemented. Its absence is an unimplemented execution safeguard, not a causal explanation for the saved offline output errors; none of these calls is shown to have reached an RPC. **Hypothesis, unproven:** a model-origin read-only capability boundary can prevent any raw model output from being treated as an executable write command, independently of whether the model learns the intended proposal. **Change:** evaluate only that origin capability in a stub harness: deny every model-origin write, while preserving the trusted-UI/executor-origin path for a canonical command assembled after exact trusted confirmation. D4 remains blocked. **Risk:** false blocks or an all-writes-off result can look safe while eliminating useful confirmed operations. **Minimum validation:** the v0.3 experiment below, with raw correctness and action decisions reported separately and positive controls through the trusted origin.

### 5. Provide task-relevant context

**Evidence:** the v0.1 serialization audit measured repeated/empty context fields over 244 assigned rows; it did not measure attention or prove context caused errors. B shows useful receipt bodies can matter for some static policy questions; C's ID-only row has no body to retrieve. **Hypothesis, unproven:** irrelevant or duplicated context may compete with task evidence in some rows. **Change:** after the firewall experiment, test one context projection rule preserving every required trusted source and provenance field. **Risk:** removing a field that disambiguates actor, page, version, or result can worsen grounding/safety. **Minimum validation:** byte-paired old/new context on a reviewed slice with field provenance, no loss of needed evidence, and fixed model/system/evaluator; report token-length and task outcomes.

### 6. Add state-complete authoritative backend receipts

**Evidence:** B static policy receipts improve full-pass 11/39→32/39 across 7 states but include 4 strict regressions; backend receipts span 9 rows/2 states and receive zero factual correctness credit because event times are later and IDs mismatch. Sixty backend rows remain blocked. **Hypothesis, unproven:** complete, correctly timed, ID-bound service receipts may improve grounding beyond static rule text. **Change:** only in a separately authorized future data version, capture a new v0.3 state-complete Scenario from a real Backend state/real RPC and serialize its Context from that same snapshot. Preserve the actual `observed_at`; make the new `generated_at`, `financial_version`, and ID binding internally consistent. This creates new evidence and does not backfill an old v1 scenario or rewrite its time/IDs. **Risk:** mutable-state timing, UUID/scope mismatch, or incomplete DTOs can turn “authoritative” data into leakage or false evidence. **Minimum validation:** audit source, snapshot-time consistency, ID binding, and schema before generation; compare the same fixed model on paired receipt/no-receipt inputs whose Context and receipt refer to that same new snapshot, and keep blocked cases blocked. Do not reconstruct the 60 blocked rows from old GT.

### 7. Continue 4B or test a larger model

**Evidence:** 4B improved across v1 checkpoints and some A/C metrics, while persistent proposal/tool payload issues remain. Proposal targets are larger/more nested, but that alone is not a capacity measure. No controlled larger-model comparison exists. **Hypothesis, unproven:** model capacity could matter after data visibility and runtime mapping are sound. **Change:** none in v0.3; retain current checkpoint for architecture replay. **Risk:** higher compute/cost can mask unresolved entity, contract, or gateway errors and does not prove improved safety. **Minimum validation:** only after representation/runtime baselines are corrected, run a same-data, same-input, same-evaluator size comparison on a new sealed family with preregistered row-level safety and structured correctness gates.

## Recommended v0.3 minimum experiment: write firewall replay

Use saved validation inputs and raw generations only: v1 cp33, A cp36, and C cp33 (24 records per saved candidate; 72 records total if all are present and uniquely identified). Preserve each record's original system/context/conversation and exact raw output. Do not run inference, edit the evaluator, alter inputs, or execute an RPC. This is an offline shadow dry-run plan; no Gateway currently exists, and none of these outputs has been shown to execute a real RPC. Both arms run identical parsing, schema validation, and common Scope/intent allowlist checks. Change only the **model-origin write capability**: arm 0 records the common-check decision with that capability hypothetically enabled; arm 1 denies every model-origin write, including outputs that claim confirmation. In both arms, an identical trusted-UI/executor-origin positive path accepts a canonical command only when paired with exact trusted confirmation and current server binding. Both paths terminate at a no-op recorder; they never dispatch to a database. Do not describe arm differences on a row that fails the identical common schema/allowlist checks as a firewall gain. Do not override a currently disabled Scope permission to manufacture an arm difference.

The proposed gate rejects every model-origin write `tool_call`, regardless of fields that claim confirmation; the Gateway, not the model, builds the canonical operation after a trusted UI event on a distinct origin. Common schema and allowlist checks remain identical between arms, including rejection of unsupported/disabled mappings. The capability rule must not repair arguments, synthesize a proposal, or treat a user sentence as confirmation. Read behavior remains unchanged. A/C's observed direct-write outputs are themselves schema-invalid (including an opaque result ID used where a UUID is required), so they may be rejected by common validation in both arms; count them as observed model failures, not incremental firewall interceptions. A future conformance suite should include minimally sufficient **valid-schema** model-origin L2 write-call controls without trusted UI origin, including outputs that self-assert confirmation, plus distinct trusted-UI/executor-origin controls with absent, forged, stale/mismatched, and exact confirmation bindings. These are design requirements only: do not generate or execute the vectors in this review, and do not treat them as training examples or new Contract rules.

Report two independent result groups:

1. **Raw model correctness:** preserve the frozen evaluator's original schema/type/structure/fact/safety results, before the firewall. A blocked call remains a model error if it was wrong; it is never re-labeled as a correct proposal or correct business outcome.
2. **Boundary behavior:** first report common-parser/schema/allowlist rejections separately. Among model-origin inputs that pass those identical checks, count writes denied by each arm and any denied-origin write that would pass arm 1 (must be zero). Separately count whether exact-confirmation trusted-origin positive controls are accepted in both arms and invalid/stale trusted-origin controls are rejected. If current Scope/allowlist blocks all model-origin writes in both arms, report zero end-to-end incremental effect; a separate unit conformance result may show the origin gate decision only when the same common checks pass, without changing/enabling Scope. All actual executor invocations must be zero. “Blocked” is an execution-safety result only. State each denominator and keep false-block/usefulness separate from safety interception.

This replay shows incremental end-to-end value only if a model-origin write passes the identical common checks in arm 0 and is denied by the capability gate in arm 1. If common schema or Scope checks reject every observed write in both arms, report zero incremental effect; do not claim the firewall intercepted those rows. The separate valid-schema conformance controls can test the gate unit, while trusted-origin positives test that exact confirmed business commands remain reachable through the same path in both arms. Neither result proves all business cases work or product integration is complete. Reserve a fresh sealed family for any later model-quality claim; do not create or use one in this review.

## Evidence quality and unresolved points

Confidence is high for frozen split counts, saved outputs, schema/row metrics, and the observed direct-write rows because they are recorded artifacts. Confidence is moderate for B's static manual fact judgments because they cover 39 rows across only 7 states; the reported weak result and regressions should remain visible. The backend B correctness conclusion is intentionally conservative: event time and ID mismatches prevent credit, not proof that receipt bodies can never help. C's paired result combines training and inference guide changes. Causation from guide complexity, context length, training capacity, or model size remains unproven. No unseen DTO, UUID mapping, current confirmation, live Gateway behavior, or fresh generalization result is assumed.
