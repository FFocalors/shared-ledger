## Candidate profile and wire versions

The candidate identifier is p2.read-paged-prepayment-refund.v2-candidate. Its only ProtocolVersions fields are api=2.1.0, semantic=2.0.0, operations=2.1.0, and trajectory=2.0.0. There is no execution_key field in that tuple. Do not silently substitute the earlier unreviewed api=2.2.0 draft or mix selected versions. The candidate is server-selected in a future, separately reviewed integration and has no default or automatic activation in this increment.

Four semantic kinds remain answer, clarify, read, and propose. The seven read candidates are read.activities, read.expenses, read.debts, read.refund_events, read.prepayment_accounts, read.prepayment_usages, and read.prepayment_return_events. read.activities alone permits no-scope discovery. read.continue and read.expense_repayment_progress are not operations. Continuation is a query_request or continue_request control message within the read trajectory, not a new capability. Proposal is intent recognition only; preview, confirm, confirmation-card, and all write capabilities remain disabled.

## Selected debt source and compatibility

This independent candidate explicitly selects the constant debt_source_variant=expense_debt_line. Its read.debts source is public.expense_debts, filtered by Activity or by a ledger-unit scope that the server has independently source-authorized. The candidate preserves each row's activity/ledger-unit/expense identity, debtor and creditor participant identifiers, stored base amount, and original amount/currency as separate nullable source facts. Null original amount or currency means unknown. It must not be filled from base values, converted, summed, netted, or described as the existing settlement recommendation.

The initial debt projection table is extended by the later multi-currency migrations named above: its amount is the persisted base value (numeric(20,1)); the subsequently added original_amount is nullable numeric(20,4), and original_currency is independently nullable. A zero stored base value can be valid when source constraints permit a positive original amount. Participant direction is carried by debtor_participant_id and creditor_participant_id, not inferred from the amount sign. The row has no independent financial version, so a runtime adapter must fence reads with the Activity financial_version before and after retrieval. If an original-currency filter is requested, rows with unknown original currency cannot support an exhaustive “no matching debt” answer.

Canonical P2 remains on its existing GET rpc/list_settlement_options call and Activity-level settlement-option DTO. Its pair aggregation, coalescing, response fields, parser, and callers are not replaced or reinterpreted. The new debt source is a separate profile and DTO contract. No SQL, RPC, ACL, RLS, Store, or canonical contracts change in this proposal.

The remaining read families preserve the reviewed source boundaries: expense/payer/split original values remain distinct from stored base values; refund facts preserve negative source signs; prepayment accounts and returns are Activity-scoped, while a usage child scope requires verified source relationships. Refund reads use only permitted public expense rows and validated public parent/Activity relationships. The private expense_refund_sources marker is not GET-accessible under current roles; verified_same_activity_parent means the public parent relationship was checked and does not establish that private immutable marker. If public source cannot verify lineage, mark refund coverage incomplete/unverified and reject exhaustive factual claims rather than treating unavailable marker data as no refunds. Native amount/currency, base amount, and FX rate stay separate. FX is evidence only: the candidate does not calculate conversions, totals, balances, or net positions. Numeric source limits remain column-specific: numeric(20,4) for four-scale amounts, numeric(20,1) for base amounts (including zero where permitted), numeric(20,10) for FX evidence, and signed-int64 bounds for Activity financial_version.

## DTO and context guard requirements for the later module

The actual strict Pydantic DTO and runtime parser—not the stale DTO_DESIGN.py outline—must define and reject malformed requests and outputs. Strict integer parsing rejects bool, float (including a JSON 1.0 value), string, and coercion for version fields, while enforcing 0 through 9223372036854775807. JSON Schema alone cannot distinguish an integral JSON number lexeme written as 1.0.

The branch guards must be mutually consistent. Before a read, the server must issue a fresh source-authorization grant for the requested principal, operation, scope, and criteria; this grant authorizes retrieval but is not a query-result receipt. The first read does not require its own future receipt. After a successful query, the server creates fresh query evidence bound to the actual operation and criteria. An answer requires that actual fresh evidence, not a source grant, a client value, or a merely receipt-shaped reference. Scope authorization and evidence provenance are runtime checks, not model claims. A nonempty fresh_receipt_refs list does not cure an ambiguous request with absent, unresolved, or not_authorized scope: answer must be rejected in all three cases even if the list is nonempty. Missing or unknown intent defaults to ambiguous and requires evidence; model-supplied basis and classifier fields are untrusted. Only an explicitly server-verified non_business branch can permit a source-free general answer. Keep answer, clarify, read, and propose decision allowlists consistent across context branches; read.activities alone may perform no-scope discovery.

A separate server-trusted proposal_intent branch keeps recognize-only proposals reachable without opening the ambiguity escape hatch. It may allow propose or clarify and must keep source-free factual answers false. When the target or scope is unresolved, it allows clarification only with an empty proposal-operation allowlist. Proposal results contain recognized intent only and cannot mint object IDs or refs, assert authorization, or enable preview, confirmation, cards, or writes. Allowlists for non_business, proposal_intent, read, clarify, answer, and ambiguous branches must be constrained together.

Activity/Expense UUIDs supplied by the app remain untrusted UI resolution hints. A future server resolver may source-authorize them and only then mint opaque model references. The implementation must not reject the application's UI flow by blanket-banning those incoming hints, and must never promote unresolved UUIDs to model authority.

Clarification must remain causally bound by runtime to the accepted original input plus the prior prompt, slot, and reply sequence; each clarification is one generation, invalidates stale facts, and preserves raw Unicode without normalization. The schema can enforce shapes, not classifier provenance/accuracy, authorization, currentness, causal history, or business truth.

## 2026-10-14 candidate prompt adapter continuation-hint delta

The frozen 29-pass contract context had page status but no model-visible next_page_ref. A prompt cannot safely construct read.continue_request from has_more, an untrusted conversation string, or a private receipt. The candidate therefore adds one public opaque-reference bridge without changing the operation set, protocol tuple, private parser checks, or canonical P2 behavior:

- P2ContinuationHint contains exactly query_evidence_ref, query_ref, and next_page_ref, using the existing opaque reference types.
- P2ModelContext.continuations is a tuple capped at 16 and defaults to empty. Each hint must bind to a fresh evidence ref in the same context, its exact query ref, and evidence whose page says has_more=true. Duplicate evidence, query, or next-page refs are rejected.
- When read is allowlisted and a fresh evidence item has another page, the matching hint must be present. A partial projection with no available continuation can remain visible when read is not allowed; facts remain explicitly partial.
- The backend constructs a hint only from the actual typed page result and its matching query evidence. A hint is an opaque continuation handle, not a source grant, identity, credential, or authorization. The existing private parse_p2_decision checks continue to bind query/page, operation, criteria, scope, Turn and input state.

This is a candidate DTO change only. It does not register or assemble the candidate, change the seven read names or four semantics, alter the version tuple, expose private source-grant data, or grant T1/API approval.
