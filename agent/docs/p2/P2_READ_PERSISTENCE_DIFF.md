## Persisted state and identity

`p2_candidate_turns` is an owner-scoped private budget/lifecycle row attached to the same Turn. Stable logical query IDs, operation, normalized criteria, scope descriptor, and their digests persist in `p2_candidate_queries`. The same query ID and descriptor are retained through Auth resume and process restart; a changed input or scope invalidates the query's current proof instead of silently rewriting the logical task. Reauthorization and a fresh source reread create a new receipt/read epoch for that same logical query. The already-dispatched logical read remains charged once; each additional actual GET and backend-processing interval is charged again.

Charge reservations, settlements, and unknown-consumption records are append-only. A reservation is committed before work starts. Backend time is a subset of active execution: each reservation and settlement enforces `backend_us <= active_us`, and the durable summary enforces the same relation across accumulated use and reservations. A successful GET settlement links its request digest, raw-body digest, measured bytes, and elapsed time. If execution ends with unknown consumption, Store releases the reservation only after charging its full reserved amounts. When an observed measurement exceeds its reservation, the Runtime must submit an `unknown` settlement with the full reserved charge and the measured excess in private `overrun_active_us`, `overrun_backend_us`, and/or `overrun_response_bytes`; it must reject publication of that result. The overrun fields preserve the observed excess but do not increase usable budget. A reservation cannot be settled twice. If the process dies before settlement, lease recovery records the full reservation as unknown. The Store settlement API rejects over-reservation as an `actual` result; Runtime must explicitly follow it with the conservative `unknown` settlement. Until that integration exists, the caller must not leave an observed overrun reserved indefinitely.

Page receipts bind owner, Turn, input, generation, claim/read epochs, context revision, stable query criteria/scope, source-version digest, GET request/body digest chain, elapsed time/byte accounting, and caller-supplied DTO/projection hashes. These are integrity links for candidate Store records, not complete source proof: the current schema does not retain HTTP status, Content-Range/range totals, per-GET typed DTO digests, or a query-evidence reference, and Store cannot independently verify that caller-supplied DTO/projection hashes came from the captured source body. A production adapter must pass an immutable `CapturedPage` with validated status/range, raw-body digest, typed DTO digest, source kind/reference/version, criteria stage, and query-evidence identity into an append-only Store extension before claiming source completeness. Until that integration is reviewed, receipt/hash strings alone do not establish source completeness or provenance. The capability value for a next page is never stored: only its digest appears in the historical receipt. Raw rows, facts, bearer tokens, Auth grants, active claim tokens, and continuation capabilities are absent from the private database. Old receipts remain historical but become non-current after resume, generation/input change, claim loss, or lease takeover. Resume cannot restore facts from a receipt; it must reauthorize and reread from offset zero before creating a current projection.

## Cumulative budgets

- At most 6 model POSTs total. The single repair allowance is a subtype of that budget: each `repair` reservation increments both `model_calls` and `repair_calls`, so five normal calls plus one repair reaches six. A repair cannot create a seventh POST.
- At most 4 distinct logical read descriptors. A same-ID replay with the same immutable descriptor does not consume another logical read; changed criteria/scope is rejected.
- At most 1 repair, 48 actual GET attempts, and 4 MiB of cumulative response bytes.
- The 20-second backend budget includes both `backend_get` network time and `backend_processing` time for parse, scope checks, joins, local criteria, version fences, and projection. Those timings must be non-overlapping: a `backend_processing` interval excludes time already charged to an in-flight GET. GET counts/bytes are charged only by `backend_get`; backend processing has no HTTP request or response fields. `local_processing` charges active execution without backend time. Backend time is a subset of active time at both the individual charge and cumulative-budget levels. Thus repeated reads and non-HTTP work share one cumulative backend ceiling.
- The 240-second limit is cumulative active execution. Accepted work stages reserve it before dispatch and settle measured elapsed microseconds afterward. Waiting for user input, Auth, or queue ownership does not charge active time. Reservations and charges survive waits, cancellation, and restart; no resume path resets them. A process interruption with unknown in-flight work charges the full reservation.

Backend and active-work reservations are independently capped before dispatch. The candidate Runtime integration must reserve `backend_processing` around the entire non-HTTP backend path and settle it on every exit. It must translate over-reservation into an explicit conservative unknown settlement with diagnostic excess, fail closed, and never leave an observed overrun as a publishable result. Store itself does not measure arbitrary caller CPU time and does not provide this end-to-end Runtime guarantee until wired and tested there.

## Scheduler and lifecycle hooks

New candidate assignment is accepted only through the Store's internal exact server-side profile parameter and is inserted atomically with Turn submit. A submit replay cannot add or change that assignment. The default `claim_next` and `claim_runnable` paths exclude candidate Turns. Only `claim_runnable(..., candidate_profile_id=fixed_profile)` can claim one; the caller must be a server-selected candidate worker. Candidate `transition_turn`, checkpoint save, accepted input/resume/cancel, claim/release, and process recovery update the private lifecycle, generation/input binding, and epochs in the same SQLite transaction as the existing Turn/checkpoint/event update. A legacy transition/save call against a candidate Turn fails closed rather than downgrading it.

Store startup does not by itself prove that a leased worker crashed. If a Turn has an unexpired claim lease, opening another `SQLiteAgentStore` connection leaves the live worker's reservations and candidate epochs unchanged. Startup recovery charges open reservations as unknown and advances the epochs only when the Turn has no live claim lease; an expired-lease scheduler takeover then performs recovery before the new claim. Stable logical queries and cumulative counters remain. A new claim still needs fresh Auth and source verification in the Runtime; Store records no bearer and cannot prove source visibility by itself. No business Supabase tables or SQL are touched by this slice.

`recover_interrupted_turns()` is also called by Runtime startup and must obey the same candidate lease fence. For a candidate Turn with a non-null claim token and `claim_until > now`, this path returns no recovery for that Turn and performs no reservation settlement, status event append, Turn state/revision change, candidate epoch change, or budget mutation. A second `SQLiteAgentStore`/Runtime startup is not evidence that the first worker died. Once the lease is expired or absent, the existing conservative recovery path may settle outstanding reservations once as unknown, invalidate claim/read epochs, and requeue; an old page receipt cannot be published after that CAS. This candidate-only rule leaves canonical `recover_interrupted_turns()` behavior unchanged.
