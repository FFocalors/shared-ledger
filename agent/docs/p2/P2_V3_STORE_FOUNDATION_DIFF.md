# P2 v3 Store foundation (disabled candidate)

This change adds private candidate state to the Agent's existing SQLite Store. The profile remains unassembled and disabled for Runtime/API use. It does not read Supabase, call a model, or publish any P2 fact or citation. The pinned candidate tuple is profile `p2.read-paged-prepayment-refund.v3-candidate`, API 3.0.0, semantic 2.1.0, operations 2.1.0, trajectory 2.0.0; the Store row also binds the reviewed v3 contract, schema-bundle, and source-cohort hashes. This is a local engineering candidate, not a T1 freeze, production enablement, or source authorization.

`store.py` retains the current Session/Turn database, connection and transaction layer, claim scheduler, action handling, cancellation, and recovery. Its migration loader preserves the immutable 001 migration and existing 002 migration, then loads the append-only Agent-owned `app/p2_source_store_v3_migration.sql` as version 003. The v3 rows are inserted in the same submit transaction as the Turn. Candidate assignment replay cannot add/change a pin. SQL guards prevent a Turn from joining both the v2 and v3 candidate families, and guard pins, charge history, admissions, query descriptors, attempts, wire captures, and nonce issue/use history against mutation or deletion.

The Store extension in `app/p2_source_store_v3.py` records:

- A source-admission identity before the model chooses an operation. It binds owner, Turn, current accepted input, generation, claim/authority epochs, context revision, private requested-scope locator, validated public-scope digest, and a digest of allowed UI hints. It has no query operation, query evidence, bearer, grant, or raw HTTP body. Admission GETs can be physically charged without consuming one of the four logical read slots.
- An immutable logical query after strict v3 request validation. Its operation is restricted to the seven v3 reads; the normalized criteria and scope are stored as bounded closed JSON with digests. A same-query resume can reuse the descriptor only when operation, criteria, and scope match exactly, while a new page-zero attempt has a new attempt sequence and current admission. A changed query needs a new descriptor and consumes another logical read.
- Turn-wide durable reservations and append-only charge events: six model dispatches including at most one repair, four logical reads, 240,000,000 microseconds active execution, 20,000,000 microseconds backend work (a subset of active time), 48 dispatched GETs, and 4,194,304 response bytes. Dispatch is recorded before an irreversible call. Confirmed pre-dispatch settlement releases the call slot but retains measured active work; interrupted dispatched work conservatively settles once as unknown. Resume, a second Store connection, and worker claim changes do not reset these totals.
- Per-query page-attempt sequence and one-time continuation issue/use hashes. Continuation consumption is bound to the current owner/Turn/query, authority epoch, criteria/scope, latest attempt and contiguous page; the raw continuation string is never stored. Claim release, cancellation, worker retirement, or recovery invalidates prior authority. A same-query offset-zero retry is permitted only with a fresh current claim/admission and immutable descriptor.
- A bounded HTTP wire-capture row linked to a settled GET reservation. Its state is always `cost_only`; it retains status, Content-Range, returned count, response byte count, request digest, body digest, source role and private attempt/admission links, but not the response body or decoded rows.

`record_p2_v3_wire_capture_cost_only` is deliberately not source evidence. There is no accepted raw-response parser, typed DTO digest, public projection digest, QueryEvidence writer, or facts/currentness publisher in this Store slice. The continuation issue helper is an internal seam only; its synthetic hashes in nonce tests exercise nonce CAS, not source proof. It must not be connected to Runtime or treated as authority until a later source adapter supplies a verified strict-source proof object. The current Store extension cannot by itself prove RLS, membership, scope joins, financial-version freshness, pagination completeness, or correct source projection. It stores no authorization token or grant.

Claim handling continues through the existing scheduler. The old default claim excludes both candidate families. A single `enabled_candidate_profile_ids=(...)` scheduler call can select canonical/unassigned, v2, and explicitly enabled v3 work using the existing queue ordering and same-owner admission checks; the returned claim includes the immutable execution profile. No second worker pool or API client selector is introduced. Runtime/API remain unchanged and do not call these v3 methods.

CPU coverage in `tests/test_p2_v3_store_recovery_edges.py` covers v1/v2-to-003 migration and ledger/integrity preservation, an existing v2 candidate row unchanged by migration 003, atomic submit rollback and replay pinning, dual-family rejection, default-off and mixed queue ordering, strict private descriptor rejection, metadata reads versus four logical reads, same-query Auth/clarification continuation without budget reset, unknown/replayed/stale-epoch nonce rejection and two-connection single consumption, the six-call/one-repair and 48-GET recovery caps, 20-second/240-second/4 MiB cap and overrun accounting, pre-dispatch release, cost-only capture, live second-Store startup, cancel/late settlement, retirement, and real `recover_interrupted_turns` behavior. The focused file passed 21 tests.

The final new-suite run is CPU-only and uses the pinned Agent venv and D-drive SQLite/temp paths. The existing v2 candidate plus SQLite persistence compatibility run had 28 passes and one expected stale assertion: the old test `test_agent_app_migration_upgrades_valid_v1_ledger_without_touching_initial` hardcodes `PRAGMA user_version == 2`; after this append-only version 003 it is 3. The old test file was not changed. The final combined focused regression collected 60 tests: 59 passed and the same one old user-version assertion failed. The separate mock Runtime/API suite contributed 10 passes. These results establish Store lifecycle and compatibility behavior only; they do not complete P2 or authorize live external execution.
