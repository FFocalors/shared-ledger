## Implemented behavior

The runtime uses the existing v1 Turn scheduler and typed result-body contracts. Full backend read bodies are durably appended and passed to the next model decision. The memory-only bearer lease is bound to one owner and Turn, bounded by configuration, removed on terminal states, and never persisted. Auth resume preserves the current generation budget; retrying an idempotency receipt does not recreate or extend a terminal lease.

Only bounded read operations are implemented: activities, expenses and debts. Activity-list reads use scope-none; expense/debt reads require one verified activity scope. Source scope checks and financial-version checks are performed through the trusted backend adapter. A result must be complete, in capacity and within its version fence before being stored. Incomplete pages, overflow and source/version mismatch fail closed.

The P2 parser recognizes create, update and presentation proposal intents only within the verified scope and their matching canonical permissions. Runtime turns a valid intent into a deterministic statement that no preview, confirmation card, proposal or write will be created. `Gateway` remains `Unimplemented`; proposal adjustment is explicitly unavailable.

Dependency failures store closed, sanitized error events with separate P2 journal proof, revoke the memory lease and pause for explicit Auth resume. Missing proof hides the error while bounded event read-ahead continues to a following status. Clarification prompts are deterministic from typed missing slots and remain safely readable in history after resume. If auth recovery or restart loses ephemeral provenance for a stored read body, the runtime asks for a new clarification and does not send that old body as current evidence.

## Explicit limits and gaps

- A single backend call may consume bounded HTTP pages, but only a complete result with at most 16 fact items is accepted per result. The full context remains subject to v1's separate capacity limits of 16 read results, 64 typed bound references, and 48 durable evidence entries. Cross-request/restart continuation and cursors are not implemented.
- A new successful read marks older P2 provenance stale. This subset does not combine multiple operation results into one grounded answer. Old bodies stay append-only; citations to stale results are rejected.
- A zero-row result has no citation-bearing fact under the frozen answer schema. Runtime completes with a deterministic message explaining the citation limitation and requesting a new query; it does not fabricate evidence.
- Canonical `ExpenseFact` and `DebtFact` carry original-currency values. Internal expense supplements retain payment/split roles and original/base amounts, but the renderer currently prints only original-currency payment/split lines. Debt base amount and base total remain private DTO data and are not rendered as facts. No base-currency summary, net balance, total, or conversion is claimed or computed by the Agent.
- Prepayment and refund operations/semantics are not implemented. No negative-refund normalization or balance arithmetic is added.
- P2 service/Supabase readiness was not exercised as a live deployment. Provider health is instance-level and can become `ready` after a successfully parsed provider response; that state does not imply semantic quality or correctness. The LM Studio token counter requires explicit artifact, model-path, origin, hash, size and interpreter binding; its setting is off by default.
- P2 source/tests and the C diagnostic ran on the Windows host. P2 Docker deployment and container interruption/recovery were not tested; the existing P1 Docker result does not establish P2 container readiness. The D-drive model, journal and SDK paths in the configuration example are Windows-host paths and cannot be copied directly into a Linux container configuration.
