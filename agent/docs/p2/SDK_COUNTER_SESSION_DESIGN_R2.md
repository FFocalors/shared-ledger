# R2 SDK counter session design proposal

**Status: design only; not implemented or approved for counting.** This document proposes a bounded way to separate slow LM Studio SDK initialization from token measurements. It does not authorize model generation, relax the five-second measurement deadline, or revise any frozen request or result.

## Proposed lifecycle

An explicit operator-invoked preparation operation may create a private, owned SDK helper session before a measurement candidate is run. Preparation can have a separately declared bounded deadline (the artifact-only preparation API already uses an explicit maximum of 30 seconds). It must verify the configured API origin, exact loaded model key, artifact path and SHA-256, configured context window, and SDK version. It must use only already-loaded-model lookup APIs; it must never call a model-construction or autoload API. Ambiguous model identity, absent model, changed artifact, wrong context, unsupported SDK version, timeout, or protocol mismatch leaves the session unusable. Preparation is never triggered by construction, health, startup, or a normal provider request.

The helper would own one explicit-origin SDK client and serve a single-flight queue. Only one measurement may be outstanding. A small versioned IPC envelope would carry an opaque candidate ID, monotonically increasing request ID, typed prompt/template input, model binding, and the expected input/schema budget. The response must echo both IDs and the binding fingerprint. IPC is bounded in size, uses pipes rather than temporary files, and never writes prompts, model output, credentials, or token values to ordinary logs. A mismatched, duplicate, late, malformed, or cross-candidate response fails closed and invalidates the session. Results are not cached or reused across measurement requests or candidates.

Each `measure()` starts one monotonic five-second deadline before it waits for the single-flight gate. The same deadline covers queue wait, request serialization and pipe write, fresh binding checks, prompt-template application, token count, response parsing, artifact post-stat, and result delivery. There is no retry. Before counting and after counting, the helper must freshly confirm the exact endpoint, loaded model key, model path, artifact binding and context. The artifact path/stat/digest binding is checked after measurement as well. Any mismatch, timeout, SDK exception, helper exit, or deadline exhaustion returns an unavailable/fail-closed result; it cannot produce an admitted count.

The parent process owns the helper PID and lifecycle. At deadline, it terminates only that exact helper and invalidates its queue/session; no request can be handed to a replacement helper until a new explicit preparation succeeds. The caller receives the timeout result by the five-second measurement deadline. Process reaping has a separate bounded cleanup grace, recorded separately from measurement latency; during cleanup the provider remains unavailable and the gate stays closed. A public `close()` should reject new work, cancel queued work, terminate only the owned helper, and wait for its bounded cleanup. It must be safe to call more than once. It must never stop LM Studio, load/unload a model, or control unrelated processes.

## Feasibility risk and alternatives

The required pair of fresh loaded-model bindings is the main feasibility risk. The only observed `list_loaded_models` call took 2,797 ms, already more than half the full deadline, before prompt rendering and counting. Repeating that call before and after a count may exceed five seconds even after client startup is amortized. No timing for `apply_prompt_template` or `count_tokens` is available because the 13 calls timed out. Therefore this design cannot claim that a warm helper will pass.

The smallest implementation experiment would first inspect the installed SDK's documented, public methods and build a CPU-controlled lifecycle test around a fake SDK: explicit prepare, exact ID correlation, one in-flight request, deadline includes gate wait and pipe write, model/artifact/context change rejection before and after count, timeout kills only the owned helper, and close prevents reuse. No model or network call is needed for that test. A later, separately reviewed token-only candidate could benchmark the warm session without generation. It must use new source/request fingerprints and a fresh approval; the failed 13-case set is never retried under this proposal.

If public SDK calls cannot provide both fresh bindings plus counting within five seconds, there are three honest choices: keep token admission unavailable; propose a separately reviewed larger deadline and new candidate policy; or ask whether the trusted binding contract can be met by a cheaper documented SDK identity operation. The third option must still prove same endpoint, loaded artifact, and context on both sides of counting. Reusing a stale handle without a fresh binding check, trusting model key alone, skipping the post-check, or silently extending the deadline are not equivalent options.

## Approval gates before implementation or another count

1. Review and approve this lifecycle, IPC schema, process ownership, deadline accounting, cleanup grace, and exact SDK binding calls.
2. Implement only after approval, with focused CPU tests that prove the timeout and ownership properties above.
3. Freeze the new implementation, tests, SDK version, model key/path/hash/context, API origin, and candidate request hashes. Do not rewrite the existing candidate, result, or manifest.
4. Run token-only measurements only under a new approval. A successful token count is budget evidence only; it does not establish model quality or authorize generation.
