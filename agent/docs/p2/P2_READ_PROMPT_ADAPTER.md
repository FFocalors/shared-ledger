# P2 read prompt adapter candidate

This add-only candidate defines deterministic request bytes for the disabled P2 read profile. It does not change the existing provider, prompt policy, runtime, route, registry, settings, or canonical prompt behavior. It is not imported or selected by application composition.

`build_p2_request(context, config=...)` accepts a validated `P2ModelContext`, its strict JSON bytes/string, or a JSON-compatible mapping. It rejects duplicate JSON keys, extra/private fields, unsupported version tuples, invalid model copies, and non-JSON values. The context is revalidated even when passed as a Pydantic instance. User input and recent messages are serialized as data without keyword filtering, truncation, normalization, or UUID promotion; opaque refs are accepted only from the typed context.

The function returns `P2PreparedRequest` with the exact UTF-8 `body_bytes`, request/context/schema SHA-256 values, endpoint URL, version bindings, and the server-selected model ID. The body targets `http://127.0.0.1:1234/v1/chat/completions`, includes the direct P2 decision JSON Schema, and fixes temperature 0, one completion, 768 output tokens, an 8192 context window, a 6144 input-token ceiling, and a 512-token schema margin. It adds no reasoning field, tools, fallback model, or alternate transport. `n=1` is the single-completion limit; no parallel tool calls are configured because the request has no tools.

The JSON schema keeps the direct union of answer, clarification, read query, read continuation, and recognition-only proposal DTOs. Its read operation discriminator enumerates the seven reviewed operation values. Optional DTO fields are represented as nullable and required in strict output mode. Schema construction is local and deterministic; this candidate has not been submitted to an OpenAI-compatible server, so provider/API acceptance is unverified.

The model-visible content is the full validated `P2ModelContext`: typed facts, query evidence, guard, scope refs, continuation hints, and the verbatim input and recent-message text. The prompt tells the model that user text is untrusted and that text mentioning a UUID or ref does not become an authoritative ref. This is structural boundary handling, not secret or UUID text scrubbing. The builder does not receive `P2IntentContext`, `P2SourceAuthorizationGrant`, database UUID columns, or client profile selection. `P2ModelContext`'s `profile_id` remains the server-supplied candidate constant.

The source-authorized read is a two-stage flow. The model can request a direct `query_request`; the server must independently resolve the scope and issue the matching grant before the backend reads. This builder does not authorize, fetch, or verify source data. Answers still require runtime parsing against fresh result receipts. A continuation hint is a public opaque page handle built by the backend from the actual typed page result and its matching evidence; it is neither a grant nor a credential. Existing private parser checks remain responsible for matching continuation refs to the authorized query and current turn/input state.

`P2PreparedRequest` is the handoff to an exact token counter. `P2ExactTokenCountReceipt` must name the exact request hash and report the provider-specific input-token count including the serialized messages and response schema. `require_exact_token_budget` rejects a missing count, a hash mismatch, or an over-budget result before a caller may dispatch. It returns a typed approval only after checking 6144 input tokens and `input + 768 output + 512 margin <= 8192`. The counter producer must be trusted by its caller; the DTO does not authenticate it. No character/byte-size estimate is treated as a token count. The fake counter tests cover gating only, not actual tokenizer or model fit.

There is no HTTP call or network responsibility in this module. In particular, successful request construction and a synthetic count receipt do not prove context-window fit, model behavior, schema acceptance, source authorization, answer quality, or end-to-end runtime behavior.

## Verification boundary

The dedicated tests use synthetic P2 DTOs and local JSON/schema checks only. The new continuation-hint contract delta is covered by the current tests; the earlier 29-pass contract result belongs to the preserved pre-delta snapshot and must not be reported as post-delta verification. Test commands, timestamps, exits, source hashes, and output hashes are recorded in the sibling D-only evidence package. No SDK, provider, model, HTTP endpoint, database, or real user data is used.

The candidate requires a separately reviewed assembly step to connect its prepared bytes to the exact token counter and only then to a provider. Until that step is approved, it is unregistered, disabled, and not part of the current app path.
