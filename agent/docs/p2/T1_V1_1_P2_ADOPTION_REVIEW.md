# T1 Protocol v1.1.0: P2 adoption review

## Decision

The SHA-bound receipt freezes T1 protocol v1.1.0 for **offline source/schema/export review**. It is a useful design basis for a separately versioned P2 profile’s query evidence, trusted rendering, and clarification trace. It does not approve the P2 `READ_PROTOCOL_NEXT` proposal as a whole, enable any live operation, establish Supabase Auth/RLS behavior, admit data, or authorize model/training use. The receipt explicitly records `production_enabled=false`, `real_backend_acceptance=false`, `models_run=false`, `human_reviewed=false`, and `training_eligible=false`.

The receipt reports 22 package tests, 46 independent root probes, and 17 independent export checks. Its 36 listed outputs, 10 schemas, 9 source files, 7 documentation files, and 7 evidence files were each hash-checked against the listed bytes and matched. This verifies the offline frozen artifact inventory, not source authenticity from a hosted database. The frozen vendor/P2 `contracts.py` remains SHA-256 `9fd214d9d8eb43c6f5b03b1d7e95b2bef274dbf9e8be495f536f495b48a5bf2d`.

## Coverage against the P2 handoff

| Area | What T1 v1.1.0 specifies | P2 adoption status |
|---|---|---|
| Read query evidence and renderer | `QueryEvidenceObservation` binds operation, normalized criteria, backend criteria, post-filter, source/version/time, counts, query/body digests, and a page summary. The protocol requires continuous page receipts, exact stable total, source-version fencing, unique rows, and a trusted renderer that distinguishes complete backend-zero from post-filter-zero. | **Offline foundation only.** The T1 registry has six operations (three reads and three proposals), but every operation/capability execution flag and external-write flag is false. P2 v1 cannot consume T1 `query_*` citations. A new negotiated P2 profile and explicit schema/renderer mapping are required. |
| Pagination | The T1 schema summarizes `pages_seen`, `has_more`, `complete`, `range_contiguous`, `stable_total_verified`, `source_version_fenced`, `unique_items_verified`, `truncated`, and optional `expected_total`. The protocol’s private evidence design requires page receipts and a source snapshot. | **Runtime work remains.** T1 v1.1 does not define a model-facing continuation action or a durable continuation record. P2 currently checks `Content-Range`, stable totals, contiguous offsets, duplicate identities, and financial versions during a bounded read, but `_get_json_rows` returns rows and `P2BackendReadResult` retains only `complete=True`; the verified page receipts, raw query/body digests, and explicit backend/post-filter stages are not carried forward. A completion boolean cannot recreate those receipts. Preserve the actual validated receipt at fetch time before claiming T1 completeness. Cross-request/restart continuation still needs a separately approved versioned contract and recovery state. |
| Criteria mapping | T1 v1.1 models the backend stage as scope-only and treats typed criteria as local post-filters. It explicitly says this does not establish P2’s date-filter pushdown behavior. | **Needs an explicit mapping.** P2 currently pushes expense date bounds into the backend request. Do not label that request as T1’s scope-only `backend_criteria`. A new profile must either fetch the approved scope and post-filter locally within reviewed bounds or define and freeze an honest representation of the actual pushdown and its completeness semantics. |
| Empty results | T1’s typed query citation can distinguish a complete backend-empty result (`expected_total=0`, `returned_count=0`) from rows fetched but none passing a local filter (`returned_count>0`, `matched_count=0`). Offline examples exercise both shapes. Unknown total, partial pages, or failed freshness checks cannot prove absence. | **Schema concept is covered; P2 v1 is not.** The examples use `synthetic_simulation`; they are not live source evidence. A new T1-profile adapter could cite a verified query observation for a narrowly scoped empty answer. The frozen P2 v1 answer schema has no query citation, so keep its existing fail-closed behavior until a separately versioned mapping is approved. An extra outcome fact is not needed to express this within the T1 query-citation grammar, but it cannot be smuggled into v1. |
| Clarification | T1 trajectories bind a clarification reply to the immediately preceding clarification decision, preserve the original accepted input, and increment generation once. The protocol says a clarification is a user input, not a tool observation, and cannot reactivate stale evidence. | **Offline foundation only.** The new profile must map original text, clarification prompt/slot set, response sequence, history, and single generation increment into P2’s actual checkpoint/resume lifecycle. This does not implement interrupted-query continuation or durable Auth resume. Restart/resume requires fresh authorization and a fresh read before evidence is current. |
| Business-intent guard | T1 requires business intent to be trusted; a business request without permission/evidence cannot fall back to a source-free conversation answer. | **Gap in current P2 seam.** Current P2 context/harness has no `trusted_business_intent` field or equivalent gate. A no-scope request can take the generic conversation path. A new profile needs a server-trusted intent guard and negative cases for business intent with no scope, no permission, no read result, and no evidence. |
| Prepayment, repayment, refund | The frozen T1 registry contains only `read.activities`, `read.expenses`, `read.debts`, and three disabled proposal operations. It contains no prepayment, repayment-progress, or refund operation/fact. | **Not covered or approved.** Do not map prepayment into `read.debts`, turn negative refunds into positive expenses, or infer remaining/FX/net values. These require a separate source-backed DTO, typed evidence and operation design, permission/RLS review, and root/T1 version approval. |

The T1 receipt and protocol documents record a 34-row business review whose text, amounts, and scopes were correct, while provenance was insufficient for rows 21, 22, and 24. This is review context only: `human_reviewed=false`, and the three provenance gaps remain. No row bodies were opened for this adoption review.

## Smallest next step

The next step is a **new P2 version-diff/profile plan**, not a source change: root and T1 should decide whether to start a separate P2 profile based on the frozen T1 v1.1 query/clarification concepts. That plan should first pin the negotiated version tuple, read-operation registry behavior, exact P2-to-T1 criteria and result mapping, receipt retention point, trusted-business-intent input, and clarification generation/history mapping. Keep the existing P2 v1 contracts and T1 v1.1.0 freeze byte-for-byte unchanged.

Only after that decision should an authorized CPU/fake integration candidate map the three existing read operations. Before any live use, a separately frozen profile must explicitly authorize the read execution path and provide real current-user Auth/RLS, source DTO, query-range, version-fence, and result-body proof. A complete multi-page live read must carry the exact receipt chain that was verified at fetch time. Do not treat offline probes or the `p2_t1_adapter` enum value as live acceptance.

Cross-request continuation/recovery and prepayment/repayment/refund remain separate additive-version decisions; they are not included by this offline v1.1.0 freeze. Optional same-Turn list-then-select and a new zero-outcome object also remain separate design decisions; the former is not required by the original P2 wording, while T1’s query-citation shape already models complete zero outcomes offline.
