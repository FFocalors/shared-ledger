# R2 live-model closed-loop diagnostic

Status: fixture and runner design only. No R2 model generation, real Supabase request, or service enablement has occurred. This document is a new diagnostic candidate and does not amend the prior 248-test result, the earlier 17-call C diagnostic, or their evidence manifests. The provider's R2 routing prompt is still being frozen; source/request hashes and the final preregistration must be created only after that freeze and separately approved by the root agent.

## Purpose and boundary

Exercise two independent Turns through the public session/Turn API and the real P2 runtime, Harness, LM Studio provider, prompt, schema, token counter, and `P2BackendAdapter`. The adapter uses an in-process `ReadOnlyTransport` fake over a fixed `https://r2-fixture.invalid` project URL. It maps only the expected GET table/RPC routes and fails on any other host, method, route, or principal. It returns bounded JSON plus exact `Content-Range` values, so the test covers adapter HTTP parsing, DTO conversion, runtime binding, persisted body, and renderer. Authentication is a fake verifier returning one synthetic principal, and grants remain in runtime memory. No DNS lookup/socket fallback, Supabase Auth/Data API access, external backend socket, write gateway, or real-user token is permitted. This tests the adapter boundary with synthetic responses; it does not prove Supabase Auth, RLS, or a live project configuration.

The model must choose whether and how to read from the user request. The test runner must not set the semantic decision, prefill an expected read trajectory, change a raw completion, inject a result into the model prompt, or convert a failed result into a pass. On a valid model read decision, the fake transport returns its fixed JSON rows and the real backend adapter parses the complete typed result. The runtime binds and stores the complete result body. The next real provider request is built from that actual stored body. A grounded answer is accepted only if the model independently returns a valid answer citing the returned evidence; the Harness then renders the final text from trusted DTO facts.

Raw model finance text is assessed independently from the renderer output. For expenses, the raw answer must identify the expense and state both payer lines and both split lines with the exact original-currency values. For debts, it must state both recorded directions, amounts, and currencies separately. Any missing, incorrect, merged, reversed, netted, converted, or unsupported raw claim fails the model diagnostic even when Harness rendering later supplies correct fact lines. A correct Harness rewrite does not count as a correct raw model answer. Raw completion, raw parsed decision, raw finance-claim review, and rendered output are stored as separate evidence fields.

## Closed-loop assertions

The CPU runner uses one new SQLite scratch store with two separate sessions and Turns, matching its queue-isolation check. Each Turn has its own exact provider chain and memory grant; the live diagnostic may use separate scratch stores only if its sealed runner and evidence format are updated to match. Both calls use the same synthetic owner only inside the isolated test process. The runner records one independent chain per Turn.

For each chain, the runner checks these observed transitions without directing the model to take them:

1. The first raw provider completion parses as a valid `ReadDecision` for the fixture's expected operation (`read.expenses` or `read.debts`). A clarification, refusal, malformed decision, different operation, provider error, or budget failure is recorded as a failed diagnostic; there is no forced read.
2. The fake backend receives the exact parsed decision and current server-held scope binding. It returns only the corresponding typed fixture, complete and fenced by its synthetic financial version.
3. The next provider prompt contains the full actual `ModelContext.read_results[*].body` persisted by the runtime. Its canonical body hash must equal the fake DTO-to-result hash recorded immediately before that provider call. The prompt must not be assembled from an expected answer or a test-only shadow body.
4. The next raw completion must parse as `AnswerDecision(basis="grounded")` and cite the current evidence reference returned by the actual read. No code may rewrite the raw decision or replace a missing/invalid citation.
5. The final event text is recorded after `P2Harness` rendering. It must include only the typed fixture values listed above. Raw completion, parsed decision, backend source/body hashes, opaque refs, budget measurement, next-step transition, and renderer rewrite are separate fields so model text cannot be confused with trusted output.
6. No proposal, confirmation, or gateway call is possible in either fixture. The run asserts zero gateway calls and no durable proposal/preview artifacts.

The fixture checks the facts and citations, not an exact natural-language answer string. In particular, for debt it checks two distinct evidence-backed directions and currencies rather than any computed net. If the model does not complete the observed chain, the run remains failed; the fixture specification does not become a teacher-forced trajectory or a model-quality pass.

## Runner limits and token accounting

The runner uses the frozen 4B model artifact and the host-bound SDK token counter only. Candidate settings are fixed to output `768`, expected context `8192`, verified input ceiling `6144`, schema reserve `512`, and the already approved local endpoint/artifact/path bindings. The exact artifact path, SHA-256, byte size, model key/path, counter Python path, endpoint origin, and provider/prompt source fingerprint must be copied from the separately approved C candidate; no auto-load, JIT load, endpoint discovery, artifact substitution, or cap escalation is allowed. Before any generation, export the two full dynamic provider requests produced by the controlled CPU flow and run the SDK counter against those exact request payloads (including the schema). If either request exceeds the frozen budget or cannot be counted, stop and report it; do not shorten context, omit the result body, or increase limits.

Limits are enforced before dispatch and accounted in separate ledgers:

- At most 6 model calls, 4 reads, and 1 bounded semantic repair per Turn.
- A shared LM generation ledger allows at most 9 separate direct-provider diagnostic calls plus at most 12 closed-loop calls (two Turns × six each), for at most 21 provider generations. The absolute LM ceiling is 24; the remaining 3 calls are unused margin and cannot be spent without a new preregistration.
- At most 12 public runtime HTTP requests, tracked separately from LM generations. Internal test synchronization is not a public request and is recorded separately.
- Provider transport itself does not retry. One existing parser repair is allowed per Turn within that Turn's six-call cap; it does not increase the output-token cap. Every attempted provider generation, including provider errors and repair calls, consumes the shared LM ledger.
- Any stop is terminal for the candidate: no retry under a larger budget or changed fixture.

The runner counts an attempted provider generation before dispatch, including a provider error, and records every runtime HTTP call before sending it. On any cap hit, token-counter mismatch/timeout, artifact-binding mismatch, incomplete read, stale financial version, cancellation, or provider failure, it stops issuing new calls and records the failure. It never retries with a higher output cap.

## Evidence format and source binding

The CPU-only pytest can export two exact post-read messages/schema inputs when `P2_R2_CPU_EVIDENCE_DIR` points to a new, nonexistent directory. These requests use a synthetic CPU model key and a byte-estimate checker; they prove dynamic envelope construction only. Provider must apply the frozen host-bound SDK counter to the full saved messages and schema using the actual approved artifact/model/API binding before any candidate is proposed. The output `budgeted_input_tokens` from the byte-estimate CPU double is never evidence of a real token fit.

Before any live generation, freeze a separate R2 preregistration containing the prompt/provider source fingerprint, runner and fixture hashes, exact model artifact and counter bindings, canonical request hashing algorithm, contexts, budgets, stop rules, and evaluation assertions. The dynamic second request cannot be precomputed because it depends on the actual first completion and returned body. Instead, the preregistration freezes the derivation rule: each provider-call record is linked to the prior raw-completion hash, the exact accepted decision hash, the fake transport response/body hash, the persisted read-result hash, and the canonical serialized request hash. This binds the dynamic request to the sealed runner and actual preceding events without preloading model outputs.

The D-run directory is new and immutable per attempt. It will contain the preregistration, command and environment record, exact UTC start/end, process exit code, stdout/stderr, append-only per-call log, raw completions, parsed decisions, backend fixture/result hashes, request-chain manifest, rendered outputs, summary, and final file SHA-256 manifest. Logs must not contain bearer values, auth headers, real account identifiers, or real database rows. Existing 248-run and C 17-call artifacts remain untouched.

Before sealing, the controlled-transport CPU suite exercises the runner's request accounting, dynamic-body hash linkage, global/Turn caps, error stop, and cleanup. It also checks that omitting a split in raw model text is scored as a raw-answer omission even though the Harness renderer still displays the complete trusted DTO values. The suite uses no LM Studio socket and is not counted as live-model evidence. If source changes during or after a live attempt, the attempt is invalid and must be preserved as such; it cannot be silently rerun under the same preregistration.
