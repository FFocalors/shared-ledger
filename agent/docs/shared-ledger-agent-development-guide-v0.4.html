查询

“我现在还欠谁多少钱？”

“我刚还给他 100 元，记一下。”

“刚才网络断了，到底记上没有？”

依据原执行编号查询结果。已成功就展示原记录，结果不明就继续核对；不会让用户重新记一遍碰碰运气。

模型负责理解，Harness 负责执行

模型输出“回答、澄清、读取、提议”四类结果。Harness 是围绕模型运行的程序，负责对象绑定、上下文、调度、验证与恢复；Gateway 是其中的确认把关模块，不是另一台服务器。

模型不获得任意 SQL、命令行或账务写工具。确认后执行已固定命令，不再让模型改参数。

封装边界保持小而明确

Python + FastAPI + Pydantic，单应用 worker，SQLite 短事务；ModelProvider 隔离推理服务，BackendAdapter 隔离业务接口，AgentStore 隔离持久化。

未来迁移主要调整部署和配置；不同模型引擎仍需验证格式与行为兼容。详细模块与拟议接口见附录。

一次写操作必须经过的路径
  1. 理解：用户文本与页面线索进入同一轮请求，后端核对对象和访问权限。
  2. 准备：模型提出业务意图，Harness 完成参数验证，后端产生可信预览和数据版本。
  3. 保存：固定命令、摘要、提案版本、有效期与确认标识保存在本地。
  4. 确认：用户在明确的预览卡片上确认；自然语言“确认”和模型自己宣称 confirmed 都不能绕过确认接口。
  5. 执行：领取唯一执行编号；云端在一次事务中完成去重、权限与版本检查、业务写入、重算和成功回执。
  6. 回显：成功展示后端结果，明确失败说明原因，响应未知则按原编号核对。

一笔消费及付款、分摊属于一个原子单元。作废后重新录入、创建活动后记账等依赖新状态的操作按阶段预览确认；跨活动不建立自动补偿机制。

两条不能省略的实现要求

可信财务预览与正式提交复用后端计算；Agent 不复制账务算法。执行回执与账务写入同事务提交；“先调用业务接口，再保存一个成功标记”不能防止响应丢失后的重复记账。

业务规则中最容易写错的部分
  • 普通活动没有预存入口；大型 Activity 级预存跨所有有效子活动消费使用。新增预存先偿还同向旧债，再增加可用余额；相反方向的债务与预存余额各自保留，不自动抵消。新增/返还遵守现有身份、币种、额度、锁和幂等 RPC。
  • 大型子活动创建时持久化所选有效 Participant ID 子集；该子活动的 Expense payer 和每个 Split bearer 都必须属于所选范围，payer 与 bearers 可不同。Participant 身份仍来自 Activity 总名单；迁移前旧子活动保持 legacy-unscoped、不回填，旧两参数入口为新子活动配置全部有效 Participant，root 始终使用完整 Activity 名单。
  • AA base amount 尾差按当前后端的 participant_order、id 稳定顺序逐个分配 0.1 最小单位；原币 4 位小数、base 1 位小数与 FX snapshot 均按后端。
  • 付款人与分摊人可以不同；Payment 与 Split 分别守恒，不把付款金额比例自动等同为分摊比例。
  • 普通/大型活动 Final 均保留当前后端优化和币种模式；普通债务投影仍是双边事实，未执行的建议不写 Transfer。预存返还只适用于大型活动。
  • Expense 仅在当前后端权限允许时修改或删除；financial_locked Expense 财务字段及 Payment/Split 不可改，锁后只允许 presentation 更新。当前没有可调用 Expense restore RPC（旧函数对 API roles 已撤 EXECUTE）；Transfer 只可 void，不能编辑或恢复。
  • D4 旧的 AI 一律禁用规则仅是旧协议历史；新 Agent 对后端允许的财务修改提供预览并在确认后推进，不能突破 Expense lock 或绕过 RPC。
  • 关联退款只恢复实际使用过的预存；争议标记不改变余额。真实 Transfer 始终是已发生事实，void 保留历史并移除当前效果。
  • completed 由后端余额计算；archived 由 Creator 控制，归档后财务写入受后端规则限制。
  • Agent 对同一固定命令复核服务端版本；该保护不修改原 App 普通编辑的 LWW 行为。当前 Expense 更新 RPC 的版本能力必须在 P0/P3 核实，不得伪称已有 CAS。
04

开发流程：逐阶段交付与验证

工程阶段采用 P0—P6，训练阶段采用 T0—T4，两条线协同推进，替代架构稿中较粗的 M1—M4 分段。按依赖推进，每阶段完成后保存证据和续接记录；无需为普通技术细节反复等待用户决定。

P0
工程核对

建立可信的现状清单

输入：App/后端仓库、Agent 原型、业务规格、LM Studio 本机配置。

  • 读取项目说明与 AGENTS.md，确认实际分支、提交和未提交修改；不得覆盖用户工作。
  • 把每项业务能力映射到真实 RPC、参数、角色和版本字段，标明现有/缺失/冲突。
  • 核对 LM Studio 版本、模型 ID、格式、量化、上下文、端口和认证；本轮已用临时 9B 模型完成原生 host/Docker 合成请求，结果见 dev-status，探针统计已由主审核对。OpenAI 兼容 chat 空 content 列为 P2 跟进，且其统计来源已由 P0 执行员复核，见 P0 环境记录；4B部署链已完成T0实测，见T0清单；CAP与模型质量另行验收。
  • 检查旧 Gateway 测试、D4 策略、AI 协议/Scope 和训练资产；同步 T0，盘点 checkpoint、数据划分和工具失败样本。旧标签先标版本/适用性，不覆盖冻结文件，也不按名字直接混训。
  • 记录 P0 核查证据，并区分后续实现缺口：普通预存迁移已本地/云端落地；Agent 运行骨架、preview/执行回执尚未验证，列为 P1/P3 实现与集成事项；9B 原生 Docker 到宿主模型调用及探针统计已由主审核对；4B部署链已有T0实测证据；CAP与模型质量另行验收。P0 可在现状、映射、环境/资产核查有证据且未决项已分派后结束，不要求先实现 P1/P3 功能。

交付：工程审计表、能力映射表、缺口任务列表、环境记录。

通过条件：核心路径的真实入口可定位；未知项有具体调查任务；没有把缺失功能写成已完成。工程审计不要求所有缺口此时补齐。

P1
可恢复骨架

先让程序运行和恢复，不依赖模型碰运气

前提：P0 完成基本路径与权限核对。

  • 建立单服务模块、四张本地表、数据库迁移、状态机、协议和 MockModelProvider。
  • 实现登录验证、会话归属、结构化页面上下文接收、轮询事件和基本限流。
  • 交付 Agent Dockerfile、Compose、配置模板、启动/停止/状态脚本；同步 T1 冻结工具注册表和语义协议，准备可验证的训练轨迹。
  • 实现重启恢复、重复请求去重、待确认暂停；数据库落盘后才向客户端承诺已接收。

交付：可启动的 Agent 骨架、协议快照、Mock 场景、运行说明。

通过条件：模拟查询/澄清/提案状态可恢复；不同账号不能读取对方会话；重新创建容器不丢状态。尚不开放真实业务写入。

P2
真实只读

接 LM Studio 与业务事实

前提：P1 接口与持久化稳定。

  • 实现 ModelProvider 的本地接口适配；验证四类语义输出，限制调用次数、上下文与超时。
  • 接活动、消费、债务、预存等读取能力；模型获得必要结果正文，不只拿一个结果编号。
  • 实现页面对象校验、实体引用绑定、多义澄清和金额事实卡片。
  • 记录真实延迟、显存、繁忙和失败情况；冻结模型及提示词基线，准备独立留出集与质量门槛。

交付：真实查询演示、模型配置记录、初次评估报告及待改进样本。

通过条件：接口与权限链路通过，能够运行未训练/当前 checkpoint 的诊断评测，记录查询、澄清和工具调用失败；模型离线不导致任务失踪。模型尚未达标不阻止完成工程基线，但不允许声称查询能力已验收，质量缺口进入 T2/T3。

P3
确认写入

先验证最关键的一条可靠执行路径

前提：真实身份、读接口和拟议语义协议可用；准备隔离测试数据。P3a 先用确定性 Mock 完成预览、确认及原子执行；P3b 与 T3 使用同一真实模型联调，共同完成核心端到端验收，不互相等待对方先验收。

  • 先接新增消费，再接已有消费的金额/付款/分摊修改。
  • 补齐后端预览、事务内权限和版本校验、唯一执行键、回执以及审计。
  • 实现确认、调整、取消、过期、重复确认与结果未知恢复；固定确认后的命令。
  • 旧 D4 全局禁用样本转为历史参考；新增可执行与拒绝边界：未锁定且后端允许的 Expense 修改经预览确认，locked Expense 财务修改拒绝并仅可走 presentation 更新。真实 Transfer 不改写。
  • 现 Expense 财务 update RPC 不提供调用方 `expected_version`/CAS；P3 为 Agent 设计自己的确认版本保护，不改变原 App LWW，也不把客户端 hint 冒充数据库 CAS。

交付：真实确认写入演示、数据库迁移草案、异常与并发测试证据。

通过条件：未确认不落业务账；同一请求无重复效果；并发改账使旧预览失效；响应丢失仍可找到原结果。不能把此阶段称为全场景首版。

P4
App 接入

形成手机端完整使用路径

前提：P3 核心执行链路通过。

  • 接个人设置开关、顶层悬浮入口、对话面板和五类消息卡片。
  • 每次发送携带当前页面快照，显示参考范围；切页不改绑旧提案。
  • 接登录刷新、后台恢复和后端事实结果；不在 App 内计算第二套账务。
  • 在获准部署的测试环境配置正式 Tunnel，使用两个账号、两台设备或等效独立客户端联调。

交付：可安装测试构建、演示步骤、配置及网络排错说明。

通过条件：真实手机网络下完成查询与确认写入；开关、换账号、断网和重启表现符合设计；主要原 App 功能不被阻断。

P5
业务扩展

逐项完成能力矩阵并回归对应训练能力

前提：App 核心路径通过；新增能力复用同一套确认与恢复机制。

  • 依次扩展活动/参与人/子活动管理、外币消费、退款、按后端权限删除 Expense、普通转账、预存返还、资金作废、普通/大型 Final 与归档管理。当前没有可调用的 Expense restore RPC（旧函数对 API roles 已撤 EXECUTE），Transfer 只能 void；不把账务事实恢复混同于 Agent 执行结果或备份恢复。
  • 每增加一种操作，补全参数、角色、预览、版本保护、执行回执和接受/澄清/拒绝用例，并同步 T4 的训练覆盖及回归；工具协议改变时重新标记数据版本。
  • 大型活动新增预存按已明确规则由任一 Member 选择 Owner/Custodian 提交，不要求 claim，也不提供 behalf 分支；返还按普通资金 actor / Creator 规则逐项映射实际 RPC。继续核对子活动权限、争议移除等确有待确认的细则；只有发现产品规则冲突才向用户提问。
  • 复合请求按固定原子单位或逐步预览处理；不引入通用工作流引擎。

交付：逐项能力映射与验收证据，未完成项保持显式标记。

通过条件：矩阵没有悄悄删掉的必做项，也没有仅返回解释却声称支持执行的写能力。

P6
首版验收

验证完整性、可恢复性与可维护性

前提：P5 必做能力接入完成，T4 发布候选及独立报告冻结，语义质量门槛已预先冻结；P6 核验该报告和最终部署，不把同一封存集的重复运行当成新的独立证据。

  • 运行核心业务金标准、权限/确认/并发与故障测试，以及独立语言评估集。
  • 从备份在干净环境恢复，验证未完成执行的核对；完成目标环境迁移演练或明确未验证边界。
  • 整理安装、配置、暂停/续接、模型替换、排错和回退说明。
  • 列出已知限制、发布范围、版本与证据；按用户授权发布测试版或正式版。

交付：发布候选、验收报告、运维说明与剩余问题清单。

通过条件：下文验收门槛全部满足，无未关闭的越权、重复记账、错误账务或数据恢复阻断问题。

不预设虚假的工期与模型准确率。

P0/T0 后按实际缺口估算工作量，P2 给出诊断基线，T1 冻结质量门槛。训练是本次明确的交付阶段；先定位上下文、协议、数据覆盖和模型问题，再安排针对性训练，不用训练掩盖工程缺陷，也不默认更换模型。

04B

模型训练：以 Agent 工具调用为主线

训练是首版开发的必做工作，不再作为“后续有空再优化”的附属项。当前模型能力尚不能按可交付状态处理。运行骨架与数据准备可以并行；最终必须用训练后的实际部署模型，在完整 Harness 中验证任务完成情况。

Teacher · 保持既有路线

OpenCode Go 套餐中的 DeepSeek Flash

沿用用户指定的渠道与模型称谓，不擅自替换为其他供应商或模型。T0 核对真实 provider、model ID、调用方式、认证与可用额度，写入配置记录；未核对前不把“DeepSeek Flash”假定为某个确定 API 标识。

Teacher 用于离线生成、补全和审核候选训练样本，不进入 App 的在线回答或故障兜底路径。在线 Student 推理仍在笔记本 LM Studio；教师是训练阶段已指定的远端依赖。只发送合成业务状态、虚构身份和规则，不上传真实账本或凭证。

Student · 继续既有训练资产

核对 checkpoint，再开展增量训练

优先复核既有 Qwen3.5-4B、LLaMA-Factory / QLoRA 路线及 checkpoint、adapter 和训练配置。历史记录可复用，但不宣称当前权重已达标；如与 LM Studio 部署格式存在差异，必须验证导出或转换路径。

训练与在线推理共用笔记本资源，默认错峰；先暂停新推理、等待或取消当前生成，再通过 LM Studio 卸载实际驻留模型以释放显存。仅停止接收请求不会释放权重。保留 Agent 和未决执行核对能力，训练后重新加载已记录模型并验证就绪。Docker 仍只封装 Agent，不将训练环境作为在线启动依赖。

工具调用能力包括“选对工具、给对参数、读懂结果、决定下一步”。

只输出合法 JSON 或背出工具名不算通过。模型可以选择已注册读能力并提出写意图；Harness 负责校验和实际执行。写意图必须进入可信预览与用户确认，不能通过训练给模型增加直接写账权限。

结果依托与多步调用查询 → 消费真实返回数据 → 补查或回答/提议；空结果、分页/截断、权限拒绝、超时。逐步实际执行读工具，核对每轮输入输出；工具名正确但参数或结果引用错误仍失败。
澄清与继续缺信息时只问必要问题；得到回答后保留原目标和已确认字段；切页与明确文字目标冲突。多轮回放检查语境保持、澄清是否必要和最终任务成功，不能只测第一条回答。
写提议与确认边界新增、修改、删除、作废等 propose；预览调整、取消、过期与冲突；不因用户催促跳过确认。检查拟议操作和参数是否正确；实际写入只由 Gateway 在确认后触发。错误提议被拦截也须计入模型错误率。
工具输出中的不可信文本账目备注中夹带“忽略规则”“直接执行”等内容；伪造成功消息与跨用户要求。模型不将业务文本当系统指令，Harness 不开放额外工具，最终无越权副作用。
样本生产与质量控制
  1. 以正确状态为起点：用隔离测试后端或确定性夹具生成活动类型、成员权限、金额和版本；期望账务以业务后端及金标准为准，不交给 Teacher 自行算账定答案。
  2. Teacher 生成候选：提供允许的工具定义、当前状态和目标，让其生成表达、澄清及 assistant/tool 多轮轨迹。教师输出是候选，不是裁判。
  3. 轨迹真实回放：Teacher 提出的调用由验证器在测试环境执行，工具结果来自执行反馈；不能用 Teacher 编写的虚构工具返回作为成功证据。失败轨迹进入诊断隔离区；修正并重新验证后才成为监督学习正样本。错误动作不得仅凭“负例”标签原样进入 SFT 目标；首版不额外引入偏好训练。
  4. 保存可复现字段：sample_id、场景族、规则/Schema/工具版本、Teacher 路由、生成配置、初始状态、用户输入、工具观察、目标动作、验证结果与审核状态。保留必要短解释，不要求教师生成隐藏思维链。
  5. 防止泄漏：同一业务状态及其语言改写放在同一划分；按活动/状态族隔离 train、validation、sealed test。去重并检查近重复，先划分再扩写。
  6. 人工复核：优先检查资金影响、权限边界、多步调用和所有自动验证失败；抽查自动通过样本。修订旧规则样本并重跑验证，不能只替换一句文字。
保持一个训练协议，避免格式和职责混乱

首版继续采用 answer / clarify / read / propose 四类语义输出。read 指定白名单操作与语义参数，propose 指定写意图，工具注册表由 Harness 提供；实际 RPC 名称、可信 UUID、身份与确认状态由程序管理。

如模型原生采用 tool_calls 格式，由适配层归一化到同一语义契约，并验证工具调用与返回配对。不要把旧原型自由生成 RPC 参数、新语义协议和原生 tool_calls 无标记地混训。训练样本、聊天模板和线上提示必须匹配实际部署格式。

确认后的事务执行与结果未知恢复不依赖模型再次规划；模型不通过重新生成命令来“修复”一个可能已提交的操作。

阶段协同

P0/T0 → P1/T1 → P2 基线与 T1 校准 → T2；P3a 可使用 Mock 同期开发；P3b 与 T3 是一次共同联调验收，不形成互相等待；P4/P5 与 T4 迭代，最后一起进入 P6。仅训练而不接真实工具、或仅搭框架而不验证模型，都不能交付首版。

数据回放按工程就绪程度分层

T1 在 P1/P2 只能对已实现读工具或明确标注的确定性模拟工具回放；模拟通过不等于真实后端通过。写入轨迹在 P3a 的隔离后端中由测试驱动器模拟用户确认后回放，Teacher 不持有生产写权限。P5 新增工具补齐真实回放后，其对应样本才能计入最终能力验收。每条轨迹记录工具实现版本及 simulated / backend_verified 状态。

个人开发者的维护与恢复

一次开发只推进一个可验收增量

  1. 读上次续接记录，核对分支和未提交修改。
  2. 选择一个能力或一个故障问题，明确本次完成条件。
  3. 实现最小变更，运行对应验证。
  4. 记录结果、未决项与下一步；按项目约定提交代码。

不同时重构 Agent、后端账务算法和全套 App 页面。发现旧代码问题先定位是否阻断当前能力。

日常启动与暂停

  1. 启动 Docker 与 Agent；检查 LM Studio API 并加载已记录模型，准备好后接收新推理。
  2. 项目脚本检查依赖后启动 Agent，必要时启动公网连接器。
  3. 结束开发时停止新请求，核对进行中的写入，再停止容器。
  4. 模型服务如供其他用途使用，不由项目脚本擅自关闭。

暂停不删除数据卷；模型内存不会持久保存。正在执行但结果未知的任务保留原编号，下一次优先核对。

状态丢失的边界必须说清。

本地数据库损坏且没有备份时，不能保证恢复完整会话和未确认草稿。云端已提交账务与回执仍然保留；恢复工作先围绕执行结果核对，不重新生成同一业务写入。

恢复旧备份时防止再次提交

执行编号必须由固定 namespace、actor_id、proposal_id 和 revision 确定性生成，或使用具备同等稳定性的既有方案；不能在每次确认时随机重建。编号不属于授权凭证，授权仍由登录和确认状态决定。

恢复备份后先进入恢复检查：对恢复出的待确认与未决提案，按可重建的原执行键查询云端终态，更新本地记录后再开放新确认。已成功则显示原结果；closed / rejected 不再提交。回执不存在也不能换键，需按原键执行或关闭并核对。

云端执行键及终态首版不自动清理，不能因为清日志而失去去重能力；后续保留策略需覆盖允许恢复的备份与请求重放时间。备份之前尚未保存的任务不保证恢复，不能推测原命令后自动重做。

B · 模块与语义协议
03

Harness 的六个部分

模块负责什么最小接口 / 边界
API 与身份上下文验证 JWT、会话归属和操作授权；开关只拦截新任务、继续规划及新确认，不拦截合法的既有结果核对或取消。可信 actor 从认证结果取得；UI 传入的 activity / selected entity 只是待校验线索。
Runtime推进状态、构建上下文、执行受限读循环、澄清、调度与恢复。只编排；不加载模型权重、不直接拼 SQL、不另写一套财务计算。
ModelProvider统一调用模型，返回语义决策，处理超时与取消。decide(context) → SemanticDecision；首版只有 Mock 和 Local 两种实现。
业务适配与操作注册表解析类型化引用，读取权威 DTO，映射预览、提交与回执查询。read / preview / execute / lookup_execution；每种操作有固定 Schema 和后端映射。
Gateway / Proposal校验操作、保存固定命令与预览，验证确认，发起执行。prepare_proposal / confirm_and_execute；普通 Python 模块，不增加网络跳转。
AgentStore保存会话、Turn、事件和 Proposal，以短事务更新状态。save_transition / claim_next / load_session 等少量方法；首版 SQLite，实现细节不扩散。

模型只输出四种语义

  • answer：解释已有可信结果，并引用对应事实。
  • clarify：说明缺少哪几个必要信息。
  • read：选择已注册的读能力及语义条件。
  • propose：提出操作意图与用户给出的字段。

权限、确认、版本、幂等键、UUID 最终绑定与 RPC 参数均由 Harness 确定。确认后执行固定命令不再调用模型重写参数。该四类语义属于新版 Agent 协议版本，与历史 v0.1.2 的六种 type 和旧三档 Scope 分开演进；历史 Schema 与冻结样本保持原样。

事实怎么进入模型

上下文包含已验证 scope、必要规则、近期对话、待补槽位，以及读工具的结果正文、observed_at 和版本。只提供 result_id 不够。

模型看到 expense_selected、participant_1 等类型化引用；Harness 保存其所属 Turn、活动、实体类型及真实 ID。一次任务跨多轮和重启保持映射，不按结果排序重绑；跨任务的旧引用须重新解析授权。账务数字由 DTO 驱动的事实卡片展示，模型说明不作为余额或金额来源。

用户：“把选中的聚餐改成 350 元，还是这三个人均摊。”下面是拟议语义格式，operation 不是实际 RPC 名称：

{
  "kind": "propose",
  "operation": "expense.update",
  "target_ref": "expense_selected",
  "fields": {
    "original_amount": "350.0",
    "split_mode": "equal",

C · 可信预览与原子执行
04

一次写操作：预览、确认、固定命令、原子提交

1 · 理解

补齐信息并绑定对象

模型提出意图；Harness 从后端确认对象、角色、归属和状态。多人同名、对象不唯一、付款人或分摊不清楚时先澄清。

2 · 预览

由后端生成可信影响

生成变更前后字段、金额与必要账务影响，返回一致快照下的 financial_version / entity versions。Gateway 保存 canonical command、命令摘要、策略版本、有效期与随机确认 nonce。

3 · 确认

用户确认当前这份提案

Android 展示服务端预览，用户点击确认。接口接收 proposal_id、revision、command_digest、nonce 与本次确认请求 ID，不接收可执行命令正文。

4 · 提交

固定命令进入云端事务

Gateway 检查身份、归属、开关、过期与提案状态；在本地事务中领取执行权，按用户、proposal_id 和 revision 确定稳定 execution_id；同一提案版本重试或恢复不得生成新编号。云端 RPC 在同一事务内完成幂等检查、权限/版本/金额校验、业务写入、重算与回执保存。

5 · 回显

显示后端执行结果

本地保存回执引用并完成 Turn。失败说明原因；响应不明则进入结果核对，沿用原 execution_id。模型可解释结果，但不能另行决定补写或改写。

预览尽量复用已有计算

基本设置只需字段 diff。消费财务修改、退款、资金作废等显示相关参与人的债务/预存变化；新增预存必须显示“偿还旧债 / 进入余额”两个部分。

把现有计算整理成可供 preview 与 commit 复用的后端函数。Agent 不维护第二套计算器，也不通过真正写入再回滚来生成预览。若后端缺该能力，它是对应写场景接入前的必做项。

不另造确认认证体系

首版使用服务端保存的随机 nonce 与普通登录认证，不额外引入 JWT 式 capability 服务。nonce、正文摘要、用户、会话、版本一起绑定，nonce 不进入模型上下文。

“确认”文本只引导用户点击当前预览卡片；模型生成 confirmed=true 不产生权限。修改内容会生成新 revision，使旧确认失效。

云端事务的具体顺序与幂等规则
  1. 校验真实调用者；按 (actor_id, execution_id) 查已持久化的终态回执。若命令摘要一致，返回原终态结果（成功、拒绝或已关闭）；不一致则拒绝。
  2. 未命中回执时，利用唯一约束领取该执行键，并锁定相关用户偏好与活动状态；所有此类写入采用一致的锁定顺序，并发相同请求只能产生一次业务效果。
  3. 重新检查 agent_enabled 与关闭修订；按操作分域检查创建/加入条件或当前成员权限、归档/名单状态，以及该操作适用的实体/财务版本。权限相关管理操作与资金操作使用一致的锁定约定。
  4. 重新计算金额上限、预存和结算方案；执行对应固定业务操作，保存审计并重建派生结果。
  5. 业务事实、相关版本和成功回执在同一数据库事务提交；只有账务变化更新 financial_version，管理变化使用相应实体/成员权限版本。不能先提交业务 RPC，再另发 HTTP 请求保存幂等记录。

已提交回执的查询优先于旧版本或开关检查，否则成功后的网络重试会被后续变化错误拒绝。调用者已失去活动访问权时，只返回其执行的最小状态，不泄漏当前账务详情。Postgres 行锁与唯一约束用于并发协调；具体 SQL 待核对已有函数实现。[2]

首版采用携带用户身份的专用 Agent 执行 RPC 外层，复用原业务函数；操作名称使用固定白名单，不接受任意函数名或 SQL。普通业务数据访问不使用 service_role；涉及特殊权限的现有函数必须先审计。

一次确认如何覆盖复合请求

以可明确预览的执行单元为界。一笔消费及其 Payment/Split 是一个原子单元，一次确认。同一活动内、参数已固定的少量新增消费，可通过专用批量 RPC 一次确认、整体提交；批量能力需要后端支持，不能用多个独立 HTTP 写入冒充原子事务。

跨活动、作废后依新余额重录、创建活动后再依新名单记账等依赖新状态的流程，按阶段生成预览并确认。首版不引入通用任务图、跨活动事务或自动补偿引擎；已完成的真实资金记录不得因为后一步失败而被偷偷撤销。

操作分域：创建、加入与现有活动不能使用同一前置条件
  • 创建活动：验证登录身份及创建规则；scope / activity_id 可空，不检查不存在的活动成员关系或 financial_version。预览拟创建字段；成功事务生成活动及创建者关系并在回执中返回 ID。
  • 加入活动：使用后端加入码校验路径，只返回加入所必需的最小预览；不能在加入前读取完整账本或默认公开名单。确认时重新校验加入码及加入条件，成员关系与成功回执同事务产生。
  • 已有活动操作：验证成员关系、对象归属和操作角色；财务写入比较 financial_version，其他操作比较相关实体/名单/权限状态，不要求所有操作都有财务版本。
  • 认领参与人：按后端允许的加入/认领顺序验证，在事务中落实一人一认领。并发被他人认领时拒绝旧提案；不自动换成另一个参与人。
结果未知的终结协议：关闭旧执行，再允许重新提案

仅有“成功回执”不足以证明一个迟到请求不会再执行。复用同一张 agent_execution_receipts 表与执行键，增加持久终态 succeeded / rejected / closed；不新增队列服务。

  1. 执行和关闭都在云端先争用同一个 (actor_id, execution_id) 唯一键并锁定记录，然后检查终态。不存在时在事务内创建占位；占位不能作为未完成状态单独提交。
  2. 执行先获得锁：验证固定命令、过期时间、权限和版本。成功则账务与 succeeded 同事务提交；确定的业务拒绝以 rejected 提交，确保无业务副作用。若调用内部业务函数后出错，需用子事务回滚业务部分，不能保存部分账务。
  3. 关闭先获得锁：在无已提交结果时写入 closed；之后迟到的同键执行只返回 closed。执行已经成功时，关闭只返回原成功结果，不撤销账目。
  4. 关闭请求自己超时也属于结果未知，继续核对原键；只有获取持久终态后才能决定显示成功、失败、取消或生成新提案。技术故障导致整笔事务回滚且无终态时，仍保留原键。

拟议 BackendAdapter 增加 close_execution；沿用已有 cancel 接口触发，属于取消旧授权的技术动作，不修改业务账目。权限只允许经认证的执行所有者核对或关闭自己的键；开关关闭或成员移除不阻断必要核对，但不得返回已失去访问权的账务细节。锁定顺序、异常回滚与迟到请求必须通过并发测试后才能上线。

确认有效期、关闭修订和版本前提随固定请求传入并由云端检查；成功/拒绝/关闭回执保留时先返回原终态。Agent 不能仅靠本地超时断言远端未执行。

D · 状态机与异常恢复
05

状态与恢复：保存足够的状态，控制循环

Turn 状态含义接下来
QUEUED请求已落库，等待执行资源。被进程内执行器领取后进入 RUNNING。
RUNNING构建上下文、调用模型、读取工具；step 字段显示具体进度。进入 WAIT_INPUT / WAIT_CONFIRM，或 COMPLETED / FAILED。
WAIT_INPUT需要用户补充，或需要客户端提供新的登录凭证。按 resume_state 恢复：澄清回 QUEUED；凭证刷新恢复原等待状态；已有 execution_id 则转 RECOVERING，禁止重新规划命令。
WAIT_CONFIRM当前 Proposal 已准备好；释放模型和执行资源。确认后进入 EXECUTING；调整则生成新版预览；取消则 CANCELLED。
EXECUTING已有固定 execution_id，正在调用后端；禁止模型改命令。结果明确则 COMPLETED / FAILED；响应未知则 RECOVERING。
RECOVERING按原键核对 succeeded / rejected / closed；无终态时保留原键。成功则 COMPLETED；rejected 则 FAILED；closed 则 CANCELLED。只有持久终态排除原操作继续提交后，才可新建提案。
COMPLETED / CANCELLED / FAILED本次请求的终态；保留必要结果。用户可发起下一次请求；结果未知不能标为 FAILED。

笔记本上的调度

用 turns 表的状态与入队时间组成持久队列；asyncio 执行器是调度机制，数据库是恢复依据。初始配置：模型并发 1，每用户最多 1 个运行、1 个排队任务，全局排队上限 16。

每次模型输出后释放推理资源；读请求和已确认写入不必等待下一次模型生成。等待用户的状态不占队列名额。超过上限返回可理解的繁忙状态。

循环与资源边界

初始配置：每次自动推进最多 6 次模型调用、4 次工具读取，结构错误最多修正 1 次；达到上限停止本轮并说明缺口。提案有效期初始为 10 分钟。

这些是可调工程初值，不是性能保证。上下文按模型配置裁剪；优先保留当前操作、必要事实和待补信息，不保留无限历史、不建设向量记忆系统。

认证恢复、开关与提案并发的明确规则
  • WAIT_INPUT 必须区分 missing_fields 与 auth_required。刷新认证后根据 resume_state 恢复；若已有 execution_id，一律先 RECOVERING，不调用模型重新规划。令牌只通过授权请求头提交。
  • agent_enabled 控制新会话、新输入、继续模型规划和首次确认；不阻断所属用户查看既有任务、补充核对所需认证、查询执行结果或取消。关闭后设置页保留“查看未完成任务/执行记录”的入口，悬浮入口仍隐藏。
  • 同一会话保留一个待确认写提案；查询可独立进行且不覆盖它。调整旧提案需在本地事务中校验 revision，旧 nonce 失效。用户另提写请求时先明确其是调整还是新任务，不能悄悄丢弃旧提案。
  • 确认、调整和取消通过条件更新争用同一提案状态；仅一个动作成功。已分配 execution_id 的任务不再调整正文，等待核对终态。
  • 同一 Turn 的澄清和认证恢复请求均携带 request_id，防止客户端重试重复追加输入；改参数即生成新的提案 revision，不因普通重试生成新版。

F · 全局入口与页面上下文
07

Android：全局悬浮入口 + 当前页面上下文

交互收敛

  • 启用后，在已登录 App 的各业务页面固定位置显示悬浮按钮；由 App 顶层统一提供，不要求每页各写一个入口。关闭后隐藏。
  • 点击后打开可展开的对话面板，保留底层页面与滚动位置；首版固定在右侧安全区域，避开底部操作栏、键盘和系统边缘手势，暂不增加自由拖动。
  • 对话面板只需文本消息、澄清、权威结果、操作预览、执行结果五类卡片。
  • 预览提供“确认 / 调整 / 取消”；调整可回到文本输入，不建设通用动态表单引擎。
  • 每次发送前显示“参考：当前活动 / 页面 / 选中对象”；用户可改为不参考本页。首页、设置等页面明确显示“未指定活动”。
  • 后台返回后读取状态和事件恢复；HTTP 断开不等于取消业务操作。

开关、权限与隔离

  • 推荐个人开关、默认关闭；启用说明模型和 Agent 在开发者笔记本运行，可用性受其在线状态影响。
  • 关闭时阻止新任务与确认，旧待确认提案在下次访问时按关闭修订失效；已提交操作仍可通过任务记录核对最终结果。
  • 默认不共享会话；成员在业务账本中仍能看到有权限的账目与审计。
  • 验证 JWT 后每次业务调用使用该用户的身份上下文；不共享会被切换 token 的可变全局客户端。
  • 当前角色与成员关系从后端获取，不用模型输入或可由用户修改的 metadata 授权。
这是 App 内的入口，不跨到其他 App 上方。

使用应用自身的界面层实现，不申请系统悬浮窗权限，不依赖无障碍抓屏。Android 的跨应用悬浮窗属于另一套权限能力，当前需求不需要它。[11] 登录页和系统权限窗口不显示该入口；普通弹窗或键盘出现时入口避让，对话已展开时不再重复显示按钮。

发送哪些页面信息

  • 页面类型，例如消费详情、活动总览、预存或结算页。
  • 当前活动、子活动和选中对象的标识；没有就留空。
  • 与问题有关的筛选条件，例如日期范围、参与人筛选。
  • 采集时间和客户端已知版本，供后端判断是否陈旧。

默认不发送整页截图、整个界面树、全部账目、密码、令牌或未保存表单。若用户想让 Agent 处理草稿，提供明确的“附带当前草稿”操作，只发送白名单字段，并标注未保存。

页面信息只帮它认路

“这笔”可指向选中的账目，但页面缓存中的金额、角色和可点击按钮不能用来授权或计算账务。服务端核对对象归属、当前成员权限，再读取真实数据。

例如在消费详情说“改成 350 元”：发送所选消费 ID → 后端核对并读取 → 展示实际变更预览 → 用户确认。列表上没有明确选中对象，就先问“哪一笔”，不猜第一条。

备注、标题、草稿等用户文本均作为数据处理，不能夹带新系统指令；UI 提供的操作提示也不扩大能力白名单。

切页、旧会话与待确认操作怎么处理
  1. 发送时取快照：采集底层业务页面，而非对话面板自身。打开面板不发送；用户按发送时，将文本和页面上下文作为同一请求提交。已发出的 Turn 固定使用当时快照，不因后续切页改变。
  2. 每轮重新带入：新消息携带本轮页面上下文。页面变化在聊天中用轻量提示显示；明确说出的活动与当前页面冲突时先解析，指代不明则澄清。
  3. 跨活动隔离：默认按活动恢复对应会话，首页/无活动页面使用独立通用会话；不把活动 A 的完整历史无条件塞进活动 B 的输入。每次恢复都重新校验权限。
  4. 继续旧任务：旧待确认卡片始终标明原活动和对象。切页不自动改绑、确认或取消它；用户主动返回该任务后，再核对版本与权限。首页不悄悄沿用上次活动来写账。
  5. 查看状态：离线时保留入口并提示服务不可用；不自动把失败的新输入排成以后突然执行的业务任务。已有 Turn 可以在重连后恢复状态。

怎么接模型

ModelProvider 优先接 LM Studio 的 OpenAI 兼容接口；这只是接口格式，推理仍发生在笔记本，不调用 OpenAI 云端。配置模型地址、实际模型 ID、超时、上下文长度，以及启用认证时的模型服务令牌。[12]

首版选用 /v1/chat/completions；对话历史与业务状态由 Harness 管理。模型只返回 answer / clarify / read / propose，所有读写工具和确认流程仍由 Harness 控制，不给 LM Studio 额外配置账务写入工具。

能聊天，还需验证能否稳定做任务

验证实际加载模型的名称、格式、量化、上下文限制，以及规定格式输出的成功情况。优先使用接口的结构化输出能力，但格式正确不等于业务理解正确，仍需解析、字段校验和场景测试。[13]

原 Qwen3.5-4B 是候选基线；不能根据模型文件夹名称就认定 LM Studio 加载的是同一版本。训练产物导出、转换或适配器加载在 T0/T1 先用最小样本贯通，T3 再验证正式候选质量；不假定任意训练文件都能直接导入。

实现时的网络与启停约定
  • 宿主机直连：Agent 若直接运行在 Windows，可使用 http://127.0.0.1:端口/v1。
  • Agent 容器直连：Docker Desktop 下拟使用 http://host.docker.internal:端口/v1，实际端口以 LM Studio 为准。容器内 localhost 指容器自己，不能当作 Windows。需实测解析、监听、防火墙与代理设置，不能只改一个地址就宣称接通。[10]
  • 监听范围：优先尝试最小可达范围；如需开启 LM Studio 的 Serve on Local Network，必须同时核对认证与 Windows 防火墙，仅允许需要的本机/Docker 访问路径。不能为解决连接问题将模型端口无保护地开放到整个局域网。[14]
  • 启动：项目脚本先启动 Agent 并检测 LM Studio，就绪后开放新推理；容器启动使用 docker compose up -d；展示 API、模型与公网连接的实际状态。Agent 可先启动并标记模型未就绪，仍允许授权的历史读取、结果核对和取消；新推理提示暂不可用，不能让模型健康检查阻断恢复 API 的启动。
  • 暂停与恢复：停止接收新任务，尽量完成提交核对，再执行 Compose stop，保留数据。崩溃后的执行沿用原执行键查询回执，未确认提案不自动执行。登录过期时由客户端重新授权。
  • 重启策略：容器拟用 restart: unless-stopped；只适用于 Docker 正在运行的情况，不能替代模型就绪检查，也不会自动拉起宿主机 LM Studio。[8]
迁移与备份：哪些一起搬，哪些重新配置
  • Agent 镜像或构建文件、依赖锁、Compose 配置和数据库一致性备份一起迁移；数据卷独立于容器，但仍需备份。[9]
  • 模型文件和版本记录独立保存，当前由 LM Studio 管理；不放入 Agent 镜像。凭据不写进镜像或仓库。
  • 未来服务器选定兼容模型运行服务，修改 ModelProvider 地址和必要适配；复验模型格式、显卡资源与任务表现。模型容器化属于届时的部署选项，不是当前开发门槛。
  • 同一公网入口切换前，停止旧 Agent 写入并做一致性备份；不让两个宿主同时处理同一份本地状态。云端业务账本继续保留。

接口隔离能减少迁移改动，但不能保证不同推理引擎的全部参数与输出行为完全一致。首版不引入 Kubernetes 或多机调度。

实现恢复流程时的补充约束

执行结果未知时，“没有查到回执”不能证明没有提交。保留原执行编号并持续核对，重试也使用同一编号；在排除原执行仍可能成功之前，不允许以新提案和新编号重做同一业务操作。过期、关闭和权限变化的检查不能阻断对已提交执行的必要结果核对。
